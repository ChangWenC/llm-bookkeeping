# Public interfaces — schema version 1

Authoritative contracts are `src/contracts/types.ts`; no business implementation lives in contracts. UTC ISO timestamps end in `Z`, IANA zones are explicit, identities are opaque strings. Unknown values use `{schema_version:1,value:null,reason:"..."}`. `TimeRange` is half open `[from,to)`. Body size counts UTF-8 bytes. `physical_order` is an opaque stable sortable source locator, never a lossy numeric ID. The absent-file digest is `absent`.

## Ownership and entry points

- Integration: contracts, config, CLI, package/lock, integration tests and docs.
- A: `src/adapters/**`; export `createAdapters(config): SourceAdapter[]` from `src/adapters/index.ts`.
- B: `src/store/**`, `src/review/**`; export `createStore(config): Promise<Store>` and `createReviewer(store, config): Reviewer` from respective `index.ts`. Only B writes SQLite schema.
- C: `src/publish/**`; export `createPublisher(store, config): Publisher` from `src/publish/index.ts`.
- Analytics/monthly/index consumers and manifest import/migration use concrete factories; only genuinely absent services report unavailable.

## Collection

`adapter.collect({lane, cutoff, range, budget}, {checkpoints,config}): AsyncIterable<CollectionBatch>` yields bounded batches. `store.saveCollection(batch): Promise<void>` writes events, fragments, coverage and checkpoints in one transaction. Checkpoints describe bytes saved, never semantic review. Live and history checkpoints are separate. Duplicate physical messages retain distinct event IDs; relocations must reuse source identities. No model receives permanent identity allocation privileges.

## Review and semantic transaction

`reviewer.prepare({kind,lane,period?,cutoff,output_dir?}): Promise<ReviewBundle[]>` yields at most the configured four bounded bundles. Context events are marked separately. `reviewer.accept(result): Promise<ReviewCommit>` validates and commits without any LLM invocation.

`store.commitReview(result): Promise<ReviewCommit>` is one SQLite transaction: accepted result, application-allocated fact revisions/operation IDs, precisely completed chunks, patches and outbox. Validate candidate IDs and target refs against the persisted bundle. A complete zero-fact chunk explicitly says `zero_facts:true`. Partial/deferred chunks remain resumable. Repeated acceptance of the same stored result/bundle reuses IDs and bytes; changed content for the same identity conflicts. Keep candidates create no new fact revision. Replays expose existing facts and explicit keep/add/replace/retract.

`readEffectiveFacts({range,scope?,as_of?}): Promise<FactRevision[]>` folds replace/retract over live, archived and legacy records while retaining immutable history. Unresolvable targets defer only the affected candidate. Unknown legacy assertions remain `legacy_record`.

Explicit semantic replay uses `Store.requestSemanticReplay({schema_version:1,replay_key,source,range,cutoff})` and `getSemanticReplay(work_id)`. The first request freezes only the source event identities currently persisted within the exact half-open range. Retrying a key reuses its original cutoff, identities and progress even if the clock changes; using that key for another source/range conflicts. Normal daily preparation never consumes these jobs. `prepare --kind daily --lane history --replay-id ID --output DIR` provides the original events and their current effective facts (including targets whose dates moved), with a typed `ReviewBundle.replay` scope. Keep/add/replace/retract are allowed only against that exact material and current target refs. Application chunk identities include the replay work; permanent event/fact identities are not renamed. Review progress records exact source slices in that work namespace in the same semantic transaction. Partial/deferred/stale-target work stays pending. Actual newly reviewed slices may mark previously unreviewed daily sources; existing daily completion is never cleared. No completion of a replay job asserts complete capture coverage.

## Outbox and publication

`publisher.publish(result): Promise<PublishResult>` accepts the result once, independently exports facts, applies files and queues consumers. `publisher.resume()` resumes durable pending exports/intents without repeating model review.

`listOutbox(status?)`, `markExportReady(batch_id,path)`, `listReadyBatches(consumer)` and `acknowledgeConsumer(ack)` implement export and consumer separation. Only immutable ready batches reach consumers. Export uses temporary file plus rename and ID/content verification; consumer output completes before ack. Wiki lock conflicts never block export.

`publisher.applyPatches(patches): Promise<FileOutcome[]>` applies append/exact replacement, protecting manual edits. Before target mutation, `saveFileIntent(intent)` persists complete desired bytes or deletion plus complete old backup, old/new digest and stable operation ID. `desired_bytes_base64:null` means deletion; `backup_bytes_base64:null` means old target absent. New/deleted files use explicit `absent` digest. Recovery compares target to desired and baseline: desired registers applied/noop, baseline retries, otherwise conflict. Pending is never swallowed by deduplication. All Wiki writers share one live-process-aware lock.

`PublishResult` reports fact commit, export, per-file status, consumers and pending independently. No single success boolean can hide partial state.

## CLI and configuration

`BookkeepingConfig` uses required absolute `wiki_root` and `data_dir`, fixed `analysis_timezone: Europe/Amsterdam`, fixed UTC cutover/live-start, explicit providers/whitelists and bounded review limits. CLI consumes the above ports, never invokes an LLM, and outputs one JSON value to stdout with diagnostics on stderr. Exit 0 means command executed, including ordinary pending/partial; exit 1 means unavailable/execution failure; exit 2 means invalid args/input.

## Durable patches and migration

`listPendingPatches()` returns accepted journal operations that have not reached applied/noop, including conflicts. `markPatchStatus(operation_id,status,reason?)` durably marks their publication independently of fact/chunk review. Thus a crash between `commitReview` and `saveFileIntent` still resumes from the original stable operation.

`importLegacy(LegacyImportBatch): Promise<LegacyImportResult>` is the sole migration write port: stable `migration_key`, immutable legacy facts, explicit verified/unresolved ID mappings, and typed pending work. It is transactional and idempotent; identical key with different content conflicts. Unresolved mappings never transfer confirmations or silently merge facts. Migration modules do not access SQL directly.

## Analytics privacy projection

Every fact candidate/revision carries `analytics_projection: UnknownValue<AnalyticsProjection>`. A non-null projection contains only its professional summary, cropped scopes, subject, evidence refs and attribution; consumers never derive Analytics text from the original mixed fact content. Null projection with reason is pending/excluded, including historical missing projections. Source adapters do not construct this semantic projection. Reviewer authors the projection; store copies it immutably to the application-allocated revision. A replacement never inherits the prior projection or prior confirmation.

## Weekly/monthly semantic records (second-wave contracts)

`WeeklyAnalysisInput` contains professional projections with explicit FactRef revisions, analysis range/zone, independent coverage_status, at most four prior snapshots, prior action and confirmed goal revision refs. It never contains original mixed-life fact content. `WeeklyAnalysisResult` contains a stable `logical_id+revision` snapshot, observation revision/evidence/attribution pairs, capability trends, goal gaps, direction/patterns, at most three proposed confirmations and one validation action. The preceding action is explicitly continued/narrowed/abandoned by stable revision ref. `AnalyticsReviewEvent` binds append-only confirm/reject/correct/retract to the target revision; stale revision operations are local stale events.

`ReviewBundle.analysis_context` and `ReviewResult`/`FactArtifact.analysis` carry these records. Monthly context/results have separate typed month/range/effective-facts/coverage/manual-baselines and summary/factrefs/supplement fields. The current Reviewer, Store and consumers validate and persist these typed fields. Semantic pages accumulate accepted conclusions across frozen evidence pages; monthly output and Analytics use the shared Publisher recovery path. Ordinary missing evidence/material work remains pending and visible.

Shared calendar utilities in `src/time.ts` provide explicit IANA local dates and Europe/Amsterdam Monday–Sunday ranges, including 167/169-hour DST weeks. Source precision includes `minute`; no-offset imports still require batch timezone and retain original precision.

`SourceAdapter.close()` releases open discovery handles; RuntimeServices.close() releases adapters then Store. Command-scoped runtime composition leaves sources uninitialized for status/facts/backup. Restore calls `restoreStore(input,newDirectory)` directly without opening the current database. Collection budgets may be explicitly configured via `collection_budgets`; defaults remain finite and resumable, not permanent maximum gates.

Goal and major-decision contracts use stable revision refs. New contract submissions have `confirmed:false`; only a user `confirm` event against that exact revision activates them. The goal retains subject/target_version/deadline. A decision retains subject, confirmed goal revision, UTC valid_from/to and exact trigger name/expected_value. Its trigger reads only an `AnalyticsProjection.verification` with explicit `user_explicit_verification` basis, matching subject/time and a kind=fact source revision. Inference, cwd or ordinary activity cannot trigger it. Persistently notify once per fact revision + decision revision. `AnalyticsReviewInput` distinguishes review events, goal-contract submissions and decision-contract submissions; `ReviewReceipt` makes stale or pending targets visible without revoking unrelated reviews.

Monthly queue acknowledgement: `MonthlyReviewInput.prepared_work_ids` lists only pending `prepare_monthly` work actually included in the bounded bundle for that month. Omitted IDs remain pending and are explicitly disclosed. `MonthlyReviewResult.completed_work_ids` may contain only a subset of those IDs. Store validates the subset and preserves it in the ready artifact; successful managed monthly publication completes precisely those IDs. Later/unread work must remain pending.

Frozen evidence pages: PrepareRequest accepts `fact_offset?` and `fact_snapshot?`. First preparation persists an ordered immutable FactRef list under a snapshot ID (refs only). `facts_page` on weekly/monthly input exposes `{schema_version:1,snapshot_id,cutoff,offset,next_offset,total}`. Follow-up pages use the same snapshot ID and original cutoff to read the same immutable revisions, so later historical inserts/corrections cannot reorder or disappear from that pagination. Omission remains explicit partial evidence. Weekly preparation/review uses the same `prepared_work_ids` / `completed_work_ids` subset validation as monthly, preserving later/unread work.

`FactArtifact.affected_months`, when present, is authoritative event/monthly publication scope. Consumers never derive extra months from a week start/end label. Older artifacts without this field fall back only to actual `affected_dates`. Weekly-only semantic snapshots carry their week in `analysis.snapshot`; they do not invent event dates/months.

SPEC7 professional catalogue: optional config/weekly `analytics_catalog` contains versioned stable-ref capability/direction definitions and versioned project mappings (`id`, relative `wiki_prefix`, nullable `repo_hint`/`direction_id`). Mappings supply context; they never establish attribution or expand a whitelist. Weekly `goal_page_baselines` are bounded exact configured page evidence, not confirmed goal contracts.

`analytics-review` accepts `kind:capability_candidate` with a candidate definition, and append-only review events may explicitly select exact `observation_ref × capability_ref` pairs. Generic observation confirmation never confirms all its capability pairs. `retracts_review_id` targets one previous review effect. Catalogue definition promotion requires explicit user confirmation of that revision. `consume analytics` may return typed `analytics_pilot`: four professional weeks only, coverage/pair review/notification/action counts; current notices respect subject, confirmed goal/decision contract, expiry and fact withdrawal. No new source scan or permissions are introduced.

Monthly original context is separate from facts. `page_paths` includes explicit safe daily/project pages with bounded full-digest baselines. `archive_contexts` contains queued immutable v2 original excerpts and known fact_refs without allocating duplicate facts; `archive_context_page` supplies bounded work offset/next_offset/total. Continue with original cutoff. A large entry’s `excerpt_reason` must specify how to increase the configured material budget and re-read that entry to reach its tail. `completed_archive_context_ids` accepts only actually included full-original context IDs, never an unread/excerpt entry; successful monthly publication completes exactly those IDs.

`src/analytics/pilot.ts` exposes pure `analyticsPilotStats(config,{as_of,coverage,reviews,notices,actions})`; callers provide already applied professional exact-ref events, historical unique notices with as-of active flags, and immutable action events. Counters cover four completed Europe/Amsterdam Mon–Sun periods (DST-aware), while active notice/action counts reflect the current as-of fold, including still-active older records. Generic observation confirmation counts zero capability pairs. `goalActiveAt` and `decisionActiveAt` use exact current-revision confirmation supplied by Store, matching goal ref/subject and contract expiry; registration flags grant no authority. These helpers do not scan sources or expand permissions. Store persists the professional action/notice/review ledgers and Analytics consume returns these statistics.

Pilot `review_duration_ms` is explicitly unknown (`value:null`, reason `Actual review duration was not measured`). Preparation/publication wall-clock intervals are not measured human review duration.

Codex heartbeat compatibility is a bounded metadata correction, not a fact retraction. Normal daily `prepare` and `getContextEvents` verify only their selected finite event page against immutable JSONL row fragments; `listEvents` also reconciles only its requested limit/cursor page. These reads can write corrected source classification/context and local `event_classification` pending work. A complete user heartbeat plus the exact same raw turn ID, source/account/conversation, locator and generation proves an assistant automation turn. Missing or inconsistent evidence remains locally unknown; quoted packets and ordinary human turns retain their classification. An indexed nearest-user lookup supplies at most one additional anchor per assistant. No opening-time or historical pending-chunk scan is added. Existing pending chunks remain historical material; new preparation rebuilds from current sources. Acceptance of an unaccepted stale bundle requires fresh preparation if any provided source or context is now excluded. Already accepted results, facts, fragments and exports are unchanged and retain their idempotent reuse path.


## Source-scoped daily preparation and WeChat policy

`PrepareRequest.source?` selects one provider before any event query limit. `range?` is an explicit UTC half-open manual daily scope; it cannot combine with `period` or `replay_id`. `max_bundles?` is a positive safe integer no larger than configured `limits.bundles_per_round`. CLI exposes these as `prepare --source PROVIDER --from UTC --to UTC --max-bundles N`; omitted source keeps fair total allocation: one oldest pending bundle per provider, then oldest remaining pending material up to the same total budget. It never gives every provider four bundles.

New daily bundles declare `source` and contain source/context events from that one provider. Primary/context events and coverage are bounded to that provider's material; accepted fact context may cross providers and include eventless legacy/archived records for deduplication, except facts proven to cite currently excluded WeChat groups. Results may optionally repeat `source` and must match the actual persisted bundle. Historical accepted results retain their immutable reuse path. Older unaccepted mixed bundles require fresh preparation. `Reviewer.prepareWithOutcomes?` returns `{schema_version:1,bundles,providers}` with independent `ProviderStageOutcome` records; compatible `prepare` remains available. Provider preparation failure reports/retries locally and leaves other providers eligible. Database/storage failure remains an execution failure.

WeChat provider options support `group_allowlist?:string[]` and `private_person_registry?:WechatPersonMapping[]`. Undefined allowlist preserves the prior participation policy; an explicit empty list excludes every group. An explicit list permits only those exact native group IDs and still requires participation/mention context rules. Ignored and service chats are always excluded; ordinary private chats and FileHelper retain their policy. Malformed WeChat scope makes only that provider unavailable. Enforce scope before live/import history bodies, on already stored review/context/replay material and on unaccepted commit. Accepted results are immutable.

Each private person mapping is `{schema_version:1,wxid,display_name,wiki_path,relationship,verified:true}`, bound to its parent provider account. It requires a verified stable native private contact ID and an existing verified personal person page. Numeric per-chat sender IDs, group IDs, group-source pages and pet pages cannot establish a person mapping. Invalid/unproven mappings remain local gaps and cannot relabel events. Registry context enriches provenance; it never creates a profile or substitutes for a stable sender ID. Real registry entries stay in private local configuration.


Exact replay selection: `SemanticReplayRequest.event_ids?` is an explicit subset of at most64 unique nonempty stable event IDs, persisted sorted on the first request. CLI accepts `replay --events ABSOLUTE_MANIFEST` with `{schema_version:1,event_ids:[...]}`. Omission retains the existing whole-range request. Every selected ID must exist and match the exact provider/range/current admission policy; missing, excluded or outside IDs reject the request. Retrying a key uses its original cutoff and exact frozen IDs; changing the selected subset under that key conflicts. Source recapture may still run, but later arrivals never silently join this explicit selection. This enables separately reviewed zero-fact WeChat replay without revisiting already reviewed Codex/Claude or completing omitted slices.


Private identity context distinguishes authorship from the conversation counterpart. `event.context.person_context` identifies only a verified actual sender. `event.context.conversation_person_context` identifies an exact verified private counterpart from the parent account's registry and stable conversation ID, after private admission. It can accompany the owner's own messages without altering their sender or role; it cannot establish authorship/subject attribution or resolve an unknown/conflicting sender. FileHelper, groups, service chats and pet/group-source mappings never acquire private counterpart context.


Manual capture generation witness: optional `AdapterContext.generation_checkpoints?:readonly SourceCheckpoint[]` supplies ordinary checkpoints only as evidence for existing source generation, header and anchor validation. Adapters must not borrow their read offset, history end, parser/discovery state or completion. Explicit range capture retains an independent durable checkpoint namespace and resumes only an identical source/range/frozen cutoff. Ordinary collection excludes these scoped checkpoints. Generation/native event identities survive a fresh scoped scan when the source is proven unchanged; changed or unproven source evidence remains explicitly pending/partial rather than a false reuse claim.

Daily `ReviewBundle.review_range?:TimeRange` with optional effective IANA `review_timezone?:string` records only an explicit bounded empty-review intent (at most 32 days), copied from the actual preparation request. Metadata-only results with no chunk reviews create no affected business periods. Nonempty daily reviews derive affected dates from accepted primary events/slices and facts; broad observational source coverage never expands those periods. A range does not itself certify capture or review completion.

## Stored event read exclusions

`BookkeepingConfig.review_read_exclusions` is optional private metadata `{schema_version:1,events:[{schema_version:1,event_id,reason}]}`. An absent field or empty list preserves existing behavior. It accepts at most 100 unique exact stored IDs; IDs are nonempty, at most 256 UTF-8 bytes and contain no whitespace, controls or wildcard characters `*?[]`. Reasons are nonempty single-line metadata of at most 512 UTF-8 bytes. Unknown entry/container fields are rejected; IDs never expand to a provider or conversation. Structural schema limits count characters; runtime validation additionally bounds UTF-8 bytes. Store checks existence/identity using projected metadata without loading a source body.

`ReviewReadExclusion` / `ReviewReadExclusions` are the config DTOs. `ReviewReadExclusionMetadata` adds provider, account_id and unreviewed. Optional Store port `reviewReadExclusions(range?,source?)` returns that metadata only; `assertReviewBundleReadable(bundle_id)` checks a saved bundle's projected primary/context/original slice IDs before material parsing. Unaccepted stale material is rejected; accepted immutable result retry remains idempotent without reopening source material. Explicit material reads remain blocked even for previously accepted bundles.

Stored daily preparation, context/nearest-anchor selection, semantic replay and skip validation exclude exact protected IDs before selecting/parsing bodies, and shared prohibited fragments cannot be loaded. Excluded rows remain stored and unreviewed: they create no reviewed source, span, unit or fabricated completion. Pending coverage includes their debt. Status exposes `review.read_excluded_unreviewed_events` separately from eligible pending and a metadata-only `review_read_exclusions` list; affected provider preparation is partial rather than quiet/no activity. Capture and raw recapture are separate adapter operations and are not governed by this stored-read restriction.

The daily orchestrator checks active source material before returning it or reading external input; an explicit `--defer-active` can retain its unreviewed debt and continue peers. Read exclusions can be added to an existing round without changing its cutoff/deadlines or config identity. A configured restriction requires the Store guard. Direct explicit saved-file inspection is outside this Store port: preserve older material unopened and reprepare through the configured Store after installing restrictions.

## October 7 frozen repair ports

`PrepareRequest.selection_basis?:'event_time'|'capture_lane'` is explicit. Ordinary daily defaults to event_time; old explicit range/period without the field retains capture_lane; replay is unchanged. `candidate_continuation?:PreparationContinuation` accepts only a Reviewer/Store-created opaque cursor bound to the exact source/lane/range/cutoff/basis, kind and selection-policy identity. Unknown or changed cursor scope rejects. Provider `preparation` returns `{schema_version,state,scope,continuation,scanned:{pages,rows,elapsed_ms},deferred_units:[{schema_version,unit,reason}]}`; state is ready/more/exhausted/unavailable. Only exhausted permits source exhaustion. More means bounded scanning can continue, including empty filtered pages; unavailable means local failure, not exhaustion. Scanning caps are five pages of320 or five seconds checked at synchronous operation boundaries; a single SQL/JSON operation is not preemptible, so elapsed_ms may exceed five seconds for that operation. An active unaccepted ready item pins continuation before its source event, including unfinished slices. Deferral is local and does not mark source review complete.

Optional Store recovery ports accept explicit limits1–64 and keyset cursors: `listPublicationOutbox({schema_version,status,limit,after?}):PublicationOutboxPage`, `listPublicationFileIntents({schema_version,states,limit,after?}):PublicationFilePage`; both return `{schema_version,items,next_cursor}` with stable cursors. `getPublicationRecoveryCursor(kind)` / `setPublicationRecoveryCursor(kind,cursor)` persist rotating `ready_exports|applied_intents` audit progress. Current/pending work precedes bounded historical audits. Existing list methods remain compatible; a scheduler cannot use an unbounded fallback and claim bounded recovery. `monthlySemanticStatus(cutoff)` returns `{schema_version,cutoff,pending_count,oldest_month,months:[{schema_version,month,pending_count,oldest_at,reasons,eligible,continuation}]}` using metadata only. Unknown legacy creation times stay UnknownValue. Continuation is the frozen FactsPage when known. Work added after a snapshot remains pending.

`storageFailureCode(error,context?:'local_write'|'source_read')` classifies capacity/SQLite globally and EIO/EROFS only with local-write provenance. `markStorageFailure(error,context)` preserves cause/code and annotates the failed operation; wrap only exact mkdir/write/sync/rename operations on local shared targets, never a whole adapter. Monthly optional config `monthly_round_limits` bounds task≤120min, new semantic≤105min, starts≤96; default is those values. These are orchestration limits, not new source permission gates.

Recovery additions: `Store.getPublicationOutbox(batch_id)` reads one exact current entry before historical pages. `acceptedReviewIdentity(bundle_id)` returns only `{schema_version:1,result_id,batch_id}`; `acceptedJournalResolutionIdentity(journal_bundle_id)` returns only `{schema_version:1,resolution_id}`. These metadata lookups allow old active manifests to recover acceptance before any source body guard, without loading saved bundles. `monthlySemanticStatus(cutoff,as_of?)` keeps evidence cutoff separate from actual operation/calendar eligibility. Publisher errors after acceptance carry the complete `PublishResult` in `error.receipt`, optional execution_status=partial and `continuation:{schema_version:1,stage:export|recovery|monthly|result,status:failed,reason}`. Preserve all prior independent file/export outcomes. Integration alone owns daily/monthly CLI/runtime/manifest and prompt orchestration; C owns factory/writer/frozen display closure, B owns Reviewer/Store and SQL. Current batch and genuine pending recovery precede rolling historical verification; already applied intents remain applied/noop after deadline.

`Store.factMaterialProgress(snapshot_id):Promise<FactMaterialProgress|null>` reads only the exact immutable ref manifest, read marks and frozen work IDs' current states. Result is `{schema_version:1,snapshot_id,cutoff,total,first_unread_offset:number|null,pending_work_count,pending_archive_context_count}`: null offset proves every frozen ref read (including an empty manifest), whereas a null result provides no proof. Pending counts include missing or noncomplete IDs from this snapshot only. It never selects another/latest snapshot or includes later work. A monthly scheduler compares exact snapshot/cutoff/total and requires both work counts zero before completion; missing/mismatched proof retains debt.

`PrepareRequest.work_only` and `MonthlyReviewInput.work_only` explicitly distinguish a frozen monthly work continuation from fresh semantic material. It requires the same snapshot/cutoff, offset equal to total, all frozen refs read, no outstanding archive context and a prior accepted complete monthly conclusion. The packet contains only actually returned remaining frozen work IDs and an empty-event semantic chunk, with no facts, manual baselines or archive/source text. A complete result may close only those returned IDs. Store preserves the prior exact aggregate summary/refs/read marks and appends the immutable acceptance without adding another semantic conclusion. Unaccepted repeat preparation and accepted-but-unpublished work pages retain their original identity. First-ever empty months still use normal semantic preparation; unknown proof cannot infer work-only eligibility.

`Store.hasCompleteMonthlyConclusion(snapshot_id):Promise<boolean>` is an exact metadata-only accepted complete conclusion proof. An empty ref snapshot's `first_unread_offset=null` alone proves no prior conclusion; false uses ordinary semantic preparation, while a missing capability cannot establish work-only eligibility. It returns no source, fact or saved bundle content.

`Store.getPublicationBatchOrder(batch_id):Promise<number|null>` gives an exact batch's actual database acceptance ordinal as a positive safe integer. It is ordering evidence within this database, not model created_at, source event time or a lexicographic batch ID. Read both compared ordinals fresh from the same Store; do not persist ordinals as wall-clock/cross-database identity. Missing/ambiguous evidence returns null. C uses this proof to preserve later accepted monthly summaries and references when an older accepted partial batch resumes; absent proof is local pending, never a guessed order. Original accepted results/artifacts/exports/intents remain immutable.


## October 11 repair contract (frozen owner boundary)

Inspection CLI v2 emits compact JSON including newline of at most16384 UTF-8 bytes. Every section, including coverage/unfinished and summary, paginates. Summary contains only identity/counts/section directory/read-state; it cannot stand in for unread records. Oversized items are UTF-8-safe fragments of one stable serialized JSON item, identified by material digest/section/index, item hash, byte_start/end/total_bytes and continuation. Continue all fragments to reconstruct the complete item; no fragment/page marks review complete. Cursor binds exact saved material digest/section. Permanent bundle/event/unit IDs remain unchanged.

New daily bundles carry `review_requirements:{schema_version:1,unit_dispositions:true,inspection_version:2,completion_policy:"primary_spans_v1"}`. Existing accepted results reuse immutable identities before new validation. Old unaccepted material requires fresh preparation. Every residual subspan outside candidate references, across all admitted primary text roles, requires one exact grouped `unit_dispositions` entry: no_persistent_information, covered_by_facts with exact supplied current FactRefs, or defer. Units are original IDs plus exact UTF-8 spans; no wildcard, unseen/context unit, ambiguous pronoun or missing media can certify completion. Deferred units remain debt even if siblings complete; no durable inference/proof graph is introduced.

Preparation continues stage-by-stage: candidates/facts/coverage/baselines/bundle. Physical metadata pages are320 rows, at most5 pages or a cooperative5000ms; selected units, necessary fact revision closure, related coverage/gaps and page context all have finite work bounds and checks after each synchronous stage. The persisted opaque cursor retains selected units and context continuation and binds original scope/config/as-of snapshot. Unaccepted ready material stays pinned. `CandidatePreparation.progress` is stable real phase/frontier plus stages rows/elapsed; rotating opaque IDs alone is not progress.
